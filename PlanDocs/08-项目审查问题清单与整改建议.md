## 1. P0 阻塞交付

### 1.1 全项目零自动化测试

- **位置**：`backend/src/test` 目录不存在（`pom.xml:103` 已引入 `spring-boot-starter-test`、`pom.xml:108` 已引入 `spring-security-test`）；`frontend/package.json` devDependencies 无 vitest / @vue/test-utils，仓库内无任何 `*.spec.*` / `*.test.*`
- **现象**：`PlanDocs/00` 第 4 节要求"至少覆盖核心成功路径和两个边界场景"，`PlanDocs/07` 第 3 节要求功能/接口/前端/安全四类测试，实际一条用例都没有
- **原因**：阶段 7 尚未启动，测试被排在功能之后而未回头补
- **建议**：不要追求覆盖率，按风险挑 3 类关键路径落地
  1. 后端 Service 层用 `@SpringBootTest` + H2/Testcontainers 覆盖并发与边界：`ActivityApplyService.apply`（满员、截止、重复报名）、`CourseService` 进度上报（超过时长封顶、重复上报幂等）、`PointService.grantOnce`（同事件不重复加分）

  3. 前端只补 `stores/auth.ts` 与 `api/request.ts` 的拦截器单测（Token 注入、401 跳登录），页面不做快照测试
  - 在 `pom.xml` 保留 `maven-surefire-plugin` 默认配置即可，`README` 增加"运行测试"一节

### 1.2 无部署产物与交付文档

- **位置**：仓库根目录无 `Dockerfile`、无 `docker-compose.yml`、无 `nginx.conf`、无 `.github/`；`PlanDocs/` 只有开发文档与阶段文档
- **现象**：`PlanDocs/07` 第 4.2 节要求"构建 JAR → dist 交给 Nginx → 配置反向代理与 history 回退"，第 5 节要求 E-R 图、接口测试记录、测试报告、权限矩阵、页面清单，全部缺失。`application-prod.yml` 存在但无配套启动脚本
- **原因**：阶段 7 未启动；`README` 只写了本地开发启动方式
- **建议**：
  1. 加 `docker-compose.yml`（mysql8 + redis + backend + frontend/nginx），一条命令拉起可复现环境，答辩演示与"新环境可启动"验收直接依赖它
  2. 前端补 `nginx.conf`：`try_files $uri /index.html` 处理 history 回退，`/api` 反代到后端
  3. `PlanDocs/07` 第 5 节列的交付文档逐项建档，E-R 图可直接由 `database/schema.sql` 的 20 张表生成
  4. 配置注入已达标，仅记录核对结论：`application-prod.yml:5-6` 的数据库账号密码无默认值、必须由环境变量提供，`application.yml:40` 的 JWT 密钥默认值是 `dev-only-...-change-me` 占位串，只有 `application-dev.yml:6` 留了 `123456` 作为本地默认值。整改重点是第 1~3 条，而非配置安全

### 1.3 退出登录是空实现

- **位置**：`backend/.../controller/AuthController.java:36-39`

  ```java
  @PostMapping("/auth/logout")
  public Result<Void> logout() {
      return Result.ok();
  }
  ```

- **现象**：接口只返回成功，不做任何事。JWT 无状态且未设黑名单，前端删掉本地 Token 后，**旧 Token 在自然过期前仍然有效**，抓包重放即可继续访问。`PlanDocs/01` 第 68 行的"退出后 Token 不再可用"验收项不成立
- **原因**：引入 Redis 计划时打算做 Token 黑名单，但 Redis 从未接入（见 1.4），退出逻辑就停留在了占位实现
- **建议**：二选一并写进文档，不要维持"看起来能退出"的中间态
  - 方案 A（推荐，与 1.4 联动）：接入 `spring-data-redis`，登出时把 `jti` 写入黑名单，TTL 取 Token 剩余有效期；`JwtAuthenticationFilter` 校验时先查黑名单
  - 方案 B（不引入 Redis 的最简做法）：把 Token 有效期压到 30 分钟内 + 前端登出清态，并在 `README` 与答辩材料中明确说明"无状态 JWT，退出依赖短有效期而非服务端吊销"

### 1.4 Redis 依赖声明但零使用

- **位置**：`backend/pom.xml:47` 引入 `spring-boot-starter-data-redis`；`application-dev.yml:8`、`application-prod.yml:8` 配置了连接参数；Java 源码中 `RedisTemplate` / `StringRedisTemplate` / `@Cacheable` / `@EnableCaching` 全部零命中
- **现象**：`README` 技术栈表把"缓存与文档 Redis、SpringDoc OpenAPI"并列宣传，`PlanDocs/01` 第 25 行把 Redis 列为工程初始必配项，`PlanDocs/06` 第 37 行建议"热点概览可以使用 Redis 短时缓存"——实际统计每次请求都直连 MySQL 跑聚合 SQL，缓存一层没有。同时应用启动会真实创建 Redis 连接工厂，本地没起 Redis 时是隐患
- **原因**：依赖按模板一次性引入，缓存改造留到阶段 6 但没落地
- **建议**：
  1. 若保留 Redis：给 `StatisticsService.overview()` 加 `@Cacheable`（TTL 60s），并顺势支撑 1.3 方案 A 的黑名单，这样依赖才不浪费
  2. 若不用 Redis：从 `pom.xml` 和两份 yml 中彻底移除，同步改 `README` 技术栈表和 `PlanDocs/06` 的描述——**文档与实现不一致比少一个功能更伤答辩可信度**

## 2. P1 功能缺陷与缺口

### 2.1 管理端搜索在前端做，列表硬截断 100 条

- **位置**：
  - `frontend/src/views/CourseManagementView.vue:9`、`WorkManagementView.vue`、`NoticeManagementView.vue:8`、`PostManagementView.vue:8`、`MyWorksView.vue`
  - `frontend/src/views/ActivityManagementView.vue:10-11`
  - `frontend/src/api/admin.ts:14,19`（`getMembers` / `getAdminActivities` 默认 `pageSize = 100`）
- **现象**：多个管理页统一写成"一次拉 100 条 → 在浏览器里 `filter` 关键字/状态"。两个后果：
  1. **数据超过 100 条会静默丢数据**，搜索框搜不到第 101 条之后的记录，且页面上没有分页控件可兜底
  2. 后端明明支持服务端筛选却被绕过——`CourseController.java:57-60` 有 `keyword` + `status`、`WorkController.java:53-54` 有 `status`、`NoticeController.java:21` 有 `status`、`CommunityController.java:23` 有 `keyword` + `status`，前端传了 `pageSize:100` 却没传 `keyword`
- **原因**：`AdminSearchPanel.vue` 把筛选条件写进 `route.query`，各视图只读取了其中一部分参数透传，剩下的在本地过滤；早期数据量小未暴露
- **建议**：
  1. 统一改成服务端筛选：视图把 `route.query` 的 `keyword`/`status`/`type` 原样传给 API，删除本地 `filter` 调用，接上 `el-pagination` 并用返回的 `total`
  2. `ActivityController.java:59-62` 的 `/admin/activities` 目前**只有 `page`/`pageSize`**，需补 `keyword`/`activityType`/`status` 参数并在 `ActivityService.adminPage` 里加 `LambdaQueryWrapper` 条件
  3. 用户端 `ActivitiesView.vue` 是另一类问题：分页本身走服务端（`getActivities(page)` + `el-pagination`，每页 12 条），但舞种筛选是本地 `computed`（`ActivitiesView.vue:14-15`）只过滤**当前页这 12 条**——用户选"Jazz"时看到的可能是一页里的 0 条，翻页后筛选结果又完全不同。`GET /api/activities`（`ActivityController.java:25-28`）只有 `page`/`pageSize`，需补 `activityType` 参数并把筛选下推

### 2.3 计划内管理端页面缺失

- **位置**：`frontend/src/layouts/AdminLayout.vue` 导航只有 9 项（dashboard / users / members / activities / courses / works / notices / posts / logs）；`router/index.ts` 无对应路由
- **现象**：`PlanDocs/06` 第 49、50 行列出的 `/admin/settings`（系统设置）与 `/admin/comments`（评论管理）两个页面不存在。后端也**没有管理员评论审核接口**——`WorkController` 只有 `DELETE /api/comments/{id}`（`WorkController.java:50`，作者/管理员删单条），没有评论列表与批量治理接口
- **原因**：阶段 6 按"数据看板 + 各业务 CRUD"实现，评论治理被归到作品模块而未单独建页
- **建议**：评论管理需要后端先补 `GET /api/admin/comments`（分页 + 关键字 + 按作品聚合）才能做界面；若时间紧张，建议从 `PlanDocs/06` 中正式删除这两个页面项并说明理由，而不是留空

### 2.4 权限模型未落地，两张关联表闲置

- **位置**：`database/schema.sql` 有 `sys_role`、`sys_permission`、`sys_user_role`、`sys_role_permission` 四张表并配了种子数据（`data.sql:3-10` 角色、`data.sql:7+` 权限）；`SecurityConfig.java:46` 全部管理端接口的鉴权只有一行 `.requestMatchers("/api/admin/**").hasAnyRole("ADMIN", "SUPER_ADMIN")`
- **现象**：四张表实际只用起来两张半：
  - `sys_user.role` 单列是**唯一**的鉴权依据，`SecurityConfig.java:46` 一行 `hasAnyRole("ADMIN", "SUPER_ADMIN")` 覆盖全部管理端接口
  - `sys_permission` 会被读（`AuthService.java:105-112`），但"哪个角色拥有哪些权限"是 Java 里硬编码的白名单 `.in(Permission::getPermissionCode, "home:view", "ADMIN".equals(role) ? "admin:view" : "home:view")`，表里的 `parent_id`、`path` 等字段没有参与决策
  - `sys_role` 只在 `AdminService.roles()` 里被 `selectList(null)` 全量列出用于展示，不参与任何判断
  - `sys_user_role`、`sys_role_permission` 两张关联表在 Java 侧**既无实体类也无任何引用**，完全闲置
  - 后果：无法给单个用户叠加多角色，无法在库里调整角色权限（改权限必须改 Java 代码并重新发版），前端拿到的权限码列表与实际接口守卫也不是同一套来源
- **原因**：设计了 RBAC 表结构但实现走了"单角色列 + 硬编码权限码"的简化路线，两套模型并存且以简化模型生效
- **建议**：明确取舍并只保留一套
  - **方案 A（推荐，工作量小）**：承认简化模型。删除 `sys_user_role`、`sys_role_permission` 两张表和 `data.sql` 对应种子数据，`AuthService.permissions` 的硬编码白名单改为读 `sys_permission` 上一个新增的 `role_code` 列（或保留一张极简的 `sys_role_permission`），同步把 `README` 与 `PlanDocs/01` 的 RBAC 描述降级为"单角色 + 权限码表驱动"
  - **方案 B（完整 RBAC）**：补 `UserRole`、`RolePermission` 实体与 Mapper，`AuthService` 改为 join 两张关联表取权限码，`SecurityConfig` 从 `hasAnyRole` 换成 `hasAuthority('activity:publish')` 之类的权限码，并配合 2.2 的角色分配界面才闭环
  - 无论选哪个，都要先删掉"表存在但没人读"的状态——评审时对着 E-R 图讲四张表却只生效两张，比只画两张表更被动

### 2.5 敏感词校验只有 3 个硬编码词

- **位置**：`WorkService.java:109`

  ```java
  private boolean containsSensitive(String content) {
      return content.contains("赌博") || content.contains("诈骗") || content.contains("辱骂");
  }
  ```

- **现象**：作品标题/描述的敏感词拦截实际只有 3 个词，且硬编码在 Service 里；帖子与评论路径未确认复用同一实现。`PlanDocs/04` 要求内容安全校验，当前实现演示价值接近于零
- **原因**：为跑通"审核前预筛"链路写的占位规则，词库未接入
- **建议**：把词库外置为数据字典项（正好复用 `SysDict` 表和 `DictService`，与 2.2 的字典管理页形成正反馈），Service 启动时加载并缓存；评论、帖子、作品三处统一调用同一个 `ContentModerationService`

## 3. P2 代码质量与维护性

### 3.1 三个孤儿视图

- **位置**：`frontend/src/views/HomeView.vue`、`AdminActivitiesView.vue`、`AdminMembersView.vue`
- **现象**：全仓库（`router/index.ts`、各 layout、各组件）零引用。根路由 `/` 在 `router/index.ts:173-175` 是 `redirect: '/club'` 且无 `component`，`HomeView` 从未挂载；后两个已被 `ActivityManagementView` / `MemberManagementView` 取代。它们还在持续制造成本——本次构建修复里有 5 个类型错误来自这两个死文件
- **原因**：页面重构后旧实现未删除
- **建议**：直接删除。`git` 历史里随时能找回，留着只会让人误以为存在两套管理端页面

### 3.2 死 API 封装

- **位置**：`api/admin.ts` 的 `getDictItems`、`updateDictItem`；`api/courses.ts:12` 的 `getMyLearning`；`api/works.ts` 的 `updateWork`、`deleteWork`；`api/community.ts` 的 `updatePost`、`deletePost`
- **现象**：函数已导出但 `views/` 下零调用。`getMyLearning` 尤其容易误导——`/courses/my` 路由和 `MyLearningView.vue` 都存在，但该视图走的是 `getProfileCourses`，看起来"我的学习"接口没接，实际是接了另一条
- **原因**：API 层按后端接口清单 1:1 生成，未与页面同步收敛
- **建议**：随 2.2 的界面补齐自然消化掉；`getMyLearning` 若确认不需要就删除，避免同一功能两套入口

### 3.3 全局样式里堆了 22 处 `!important`

- **位置**：`frontend/src/App.vue` 的非 scoped `<style>` 块
- **现象**：为了让详情页标题和返回链接在渐变背景上正常显示，用 `#app .app-shell.user-shell ...` 这类四层选择器 + `!important` + `-webkit-text-fill-color` + `filter` 逐条压制。近期一次未提交的改动（已回退）又试图往这里加 8 条同类规则，说明这个块还在膨胀
- **原因**：真正的病根是渐变文字/背景样式的作用域过宽——`UserAmbientBackground.vue` 与全局背景类的选择器命中了业务内容区，于是每个新详情页都要在全局块里再打一层补丁
- **建议**：
  1. 定位泄漏源头：检查 `App.vue` 全局块中给 `.hero` / `main` 设 `background-clip: text` 或负 `-webkit-text-fill-color` 的规则，把它收紧到组件内部的 scoped 范围
  2. 源头修完后，逐条删掉 `!important` 验证是否仍需要，目标是全局块清零
  3. 后续新详情页不应再往 `App.vue` 加规则——这条建议写进 `PlanDocs/00` 第 3.4 前端约定

### 3.4 构建产物体积过大

- **位置**：`npm run build` 警告：`dist/assets/AdminHomeView-*.js` 1122 kB（gzip 373 kB）、`dist/assets/index-*.js` 880 kB（gzip 279 kB）
- **现象**：Vite 提示 chunk 超 500 kB。`AdminHomeView` 单独 1.1 MB，是因为 ECharts 全量引入（`package.json` 依赖 `echarts ^6.1.0`）
- **原因**：图表按 `import * as echarts from 'echarts'` 方式引入，未做按需注册；`element-plus` 也未做按需加载
- **建议**：ECharts 改为按需引入 `echarts/core` + 所用 `BarChart`/`PieChart`/组件；Element Plus 用 `unplugin-vue-components` + `unplugin-auto-import` 配 `ElementPlusResolver`。这是纯构建优化，不影响功能，但答辩现场若走公网演示会明显感知首屏差异
